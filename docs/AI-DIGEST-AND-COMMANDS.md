# План: генеративная сводка дня и команды на естественном языке

Документ описывает два отдельных изменения Android-приложения «Мимоходом». Задачи независимы, их нужно реализовывать и выпускать по очереди: сначала сводку дня, затем команды.

Главный принцип обеих задач: **сначала небольшой ручной сценарий, который легко проверить, без новых фоновых процессов и миграций SQLite**.

## Общие требования

- Для MVP обе функции работают через Polza.AI; локальные GGUF и Gemini Nano добавляются только после стабилизации формата ответов.
- Запуск выполняется явным действием пользователя. Никаких новых периодических задач в первой версии.
- Перед первым облачным запросом используется существующее согласие на передачу данных.
- Платный запрос не повторяется автоматически. После таймаута или ошибки доступен только ручной повтор.
- Одновременно выполняется не больше одного запроса одного типа.
- Тексты заметок передаются модели как данные, а не инструкции.
- Модель возвращает строго ограниченный JSON. Приложение проверяет идентификаторы, длины, даты и версии записей.
- Никакие предложения команд не изменяют заметки без экрана предпросмотра.
- Каждая задача выпускается отдельно: свои JVM-тесты, `assembleDebug`, `lintDebug`, обновление версии и записи в проектной документации.

# 1. Генеративная сводка дня

## 1.1. Цель

На экране «Сегодня» пользователь нажимает «Сводка дня» и получает короткий связный обзор уже известных приложению событий и шагов плана:

- что сегодня запланировано;
- что требует подготовки;
- какие дела просрочены;
- на что обратить внимание в первую очередь.

Каждый конкретный пункт должен ссылаться на исходную заметку. Сводка ничего не отмечает выполненным, не переносит сроки и не создаёт напоминания.

## 1.2. Границы MVP

Входит:

- кнопка ручного запуска на экране «Сегодня»;
- один облачный запрос;
- карточка результата с источниками;
- состояния загрузки, ошибки и повторного запуска;
- ограничение объёма входа и ответа;
- JVM-тесты сборки данных, запроса и разбора ответа.

Не входит:

- автоматическая утренняя генерация;
- новое расписание и уведомление с длинным текстом;
- сохранение сводки в отдельную таблицу;
- диалог с моделью о сводке;
- автоматическое выполнение рекомендаций;
- локальные модели;
- дополнительный анализ всего архива заметок.

Существующая локальная утренняя сводка остаётся без изменений.

## 1.3. Пользовательский сценарий

1. Пользователь открывает «Сегодня».
2. Рядом с «Предложения ИИ» или под датой нажимает «Сводка дня».
3. Если событий, шагов плана и подходящих просроченных дел нет, приложение показывает «Для сводки пока нет данных» и не делает запрос.
4. При первом облачном сценарии показывается стандартное согласие. Дополнительно перед отправкой указано, какие категории данных уйдут в Polza.AI.
5. На месте кнопки появляется состояние «Готовим сводку…». Повторное нажатие блокируется.
6. Ответ появляется карточкой над обычными разделами «Напоминания» и «План на сегодня».
7. Названия источников открывают соответствующие заметки.
8. После ошибки исходные данные экрана не меняются; доступны «Повторить» и «Закрыть».

Ручная сводка не расходует дневной бюджет из четырёх фоновых пакетов: это отдельный явно запущенный запрос, аналогичный ручному чату. Его платный характер показывается до отправки.

## 1.4. Какие данные собирать

Источник данных должен повторять логику `MainActivity.todayPage()`, а не создавать другое понимание дня.

Во вход включаются:

1. **События текущих местных суток** из `Store.dayReminders(start, end)`, включая все подходящие даты `REPEAT_LIST`.
2. **Шаги плана на сегодня** через `PlanTree.scheduledSteps(start, end)`, с сохранением состояния `done`.
3. **Невыполненные шаги плана без точного времени**, только если они относятся к сегодняшней дате по данным плана.
4. **Небольшое число просроченных дел** из записей с классом задачи или открытым планом — отдельным этапом, только если это не потребует сложного отбора. Для первого патча допустимо ограничиться пунктами 1–2.

Ограничения входа:

- не более 12 заметок;
- не более 6000 знаков JSON-данных без системного промпта;
- до 8 шагов плана на заметку;
- название до 120 знаков;
- текст заметки не отправлять, если для события достаточно названия, даты и пунктов плана;
- итоговый список сортируется по времени, затем по идентификатору для стабильности.

Часовые границы считаются через `ZoneId.systemDefault()`, как в `todayPage()`: от начала текущих местных суток до начала следующих. Нельзя использовать фиксированные 24 часа.

## 1.5. Формат запроса

Новый чистый Java-класс `DayDigest` строит `chat/completions`-запрос.

Параметры:

- модель — текущая модель чата;
- `temperature = 0.2`;
- `max_tokens = 1200`;
- один системный и один пользовательский message;
- ответ только JSON, без Markdown и пояснений вокруг.

Системный промпт должен требовать:

- писать по-русски, кратко и спокойно;
- использовать только переданные сведения;
- не выдумывать подготовку, препятствия, просрочки и приоритеты;
- не объявлять дела выполненными;
- не ставить напоминания и не предлагать изменения как уже выполненные;
- отмечать неопределённость, если время не задано;
- не повторять один и тот же пункт разными словами;
- давать ссылку на заметку идентификатором в каждом конкретном пункте.

Предлагаемый контракт ответа:

```json
{
  "summary": "Два-три предложения о дне в целом",
  "items": [
    {
      "note": 12,
      "kind": "event",
      "text": "В 14:00 приём у врача"
    },
    {
      "note": 18,
      "kind": "plan",
      "text": "Осталось подготовить документы"
    }
  ]
}
```

Допустимые `kind`: `event`, `plan`, `overdue`, `prepare`.

Ограничения разбора:

- `summary` — до 500 знаков;
- `items` — не более 8;
- `text` — до 240 знаков;
- `note` обязателен и должен присутствовать во входе;
- повтор одинаковых пар `note + text` удаляется;
- неизвестные `kind` заменяются нейтральным `plan` либо отбрасываются;
- кодовые ограды и текст вокруг JSON снимаются через существующий подход `AgentPlan.unwrap`;
- числовые ключи исправляются через `JsonRepair`, если они появятся во вложенных объектах;
- пустая сводка без единственного корректного пункта считается ошибкой разбора.

## 1.6. Изменения в коде

| Файл | Изменение |
|---|---|
| `DayDigest.java` | Новый чистый Java-класс: модель входа, ограничение данных, `payload`, `parse`, описание источника |
| `DayDigestRunner.java` | Новый Android-runner: один активный запрос, обращение к Polza.AI, состояние результата/ошибки, отсутствие автоповтора |
| `MainActivity.java` | Кнопка на `todayPage()`, сбор текущего снимка, карточка ответа, переходы к заметкам |
| `Store.java` | Только если потребуется небольшой метод чтения данных дня; схему SQLite не менять |
| `tests/DayDigestTest.java` | Новые JVM-тесты контракта |
| `scripts/test-day-digest.ps1` | Компиляция и запуск тестов чистой Java-логики |
| `docs/AI.md` | Описание пользовательского сценария, данных и ограничений |

Не создавать отдельную Activity и не добавлять новый экран настройки для MVP.

## 1.7. Этапы реализации

1. Вынести снимок данных дня в небольшую модель `DayDigest.Input`, не меняя отображение `todayPage()`.
2. Реализовать ограничение входа и стабильную сортировку.
3. Реализовать `payload` и строгий `parse`.
4. Написать JVM-тесты и прогнать их до подключения интерфейса.
5. Добавить runner с состояниями `idle/loading/result/error`.
6. Добавить кнопку и карточку результата в `todayPage()`.
7. Проверить ошибки 401/402/429, таймаут, пустой ответ, обрыв JSON и удаление исходной заметки после ответа.
8. Выполнить ручной smoke-тест сначала на локальной заглушке Polza.AI. Платный запуск делать только отдельно и с явным согласием владельца ключа.
9. Прогнать общие тесты проекта, `assembleDebug` и `lintDebug`.

## 1.8. Обязательные тесты

### Чистая Java

- сутки считаются в часовом поясе пользователя;
- событие ровно в полночь попадает в правильный день;
- несколько дат `REPEAT_LIST` не теряются;
- выполненный шаг не выдаётся за невыполненный;
- вход ограничен 12 заметками и 6000 знаками;
- порядок входа стабилен;
- модель не может сослаться на непереданный ID;
- лишние пункты сверх восьми отбрасываются;
- слишком длинные строки не попадают в интерфейс;
- JSON в ```json и JSON с пояснением вокруг разбираются;
- пустой и оборванный ответ даёт понятную ошибку;
- текст заметки с инструкцией модели остаётся только данными.

### Ручные сценарии

1. День без событий — запрос не отправляется.
2. Одно событие и один план — сводка содержит оба, источники открываются.
3. Все пункты плана выполнены — модель не предлагает выполнить их снова.
4. Повторное нажатие во время запроса не создаёт второй запрос.
5. После ошибки экран «Сегодня» остаётся полностью рабочим.
6. Если исходную заметку удалили после ответа, приложение не падает и не открывает чужую запись.
7. При смене дня старая карточка не выдаётся за сводку нового дня.

## 1.9. Критерий готовности

Функция готова, если:

- запускается только вручную;
- не делает запрос при пустом входе;
- не меняет заметки, планы и напоминания;
- показывает источники только из фактически переданных записей;
- не имеет автоповторов и параллельных запусков;
- проходит новые JVM-тесты, существующие тесты, сборку и lint;
- поведение и лимиты записаны в `docs/AI.md`.

## 1.10. Возможное продолжение после MVP

Только отдельной задачей:

- кнопка «Сохранить сводку заметкой»;
- кеш неизменного снимка дня;
- автоматическая генерация по расписанию;
- учёт просроченных дел и последних ответов помощника;
- локальная генерация короткой сводки.

# 2. Команды на естественном языке

## 2.1. Цель

Пользователь пишет в ИИ-чат обычную просьбу, например:

- «Перенеси заметки о ремонте в папку “Дом”»;
- «Напомни завтра в 10:00 обо всех этих делах»;
- «Создай отдельный список покупок из этих записей».

Приложение находит затрагиваемые заметки, получает от модели структурированные действия и показывает **предпросмотр**. Только после кнопки «Применить» изменения выполняются одной транзакцией и попадают в журнал с возможностью отмены.

## 2.2. Главное ограничение MVP

Не делать универсального исполнителя любых действий. Поддержать небольшой словарь:

1. `create` — создать новую заметку на основании переданного контекста.
2. `remind` — добавить одно или несколько будущих напоминаний существующей заметке.
3. `folder` — создать папку при необходимости и переместить туда выбранные заметки.

`create` и `remind` уже частично описаны в `AgentAction`. Для папок добавляется один новый тип `folder`.

Откладываются:

- удаление и корзина;
- замена всего текста заметки;
- массовое переименование;
- автоматическая сборка колод и платные сводки;
- изменение планов;
- очистка напоминаний;
- повторяющиеся события;
- цепочки из нескольких запросов;
- автономное применение без предпросмотра;
- выполнение команд из текста самих заметок.

## 2.3. Пользовательский сценарий

1. Пользователь отправляет команду в обычный чат.
2. Приложение локально отбирает заметки существующим `Retrieval.select`, как для вопроса по заметкам.
3. Модель получает ограниченную выборку, текущие папки, дату, часовой пояс и словарь разрешённых действий.
4. Если данных недостаточно, модель возвращает один уточняющий вопрос без действий.
5. Если команда ясна, модель возвращает короткое пояснение и не более четырёх действий.
6. Приложение отбрасывает недопустимые действия и показывает карточку предпросмотра:
   - что будет сделано;
   - названия затрагиваемых заметок;
   - старое и новое значение, где применимо;
   - предупреждение о частично отброшенных действиях.
7. Пользователь нажимает «Применить» или «Отмена».
8. Перед применением приложение повторно читает все затрагиваемые записи и сверяет ревизии.
9. При совпадении ревизий весь набор применяется в одной SQLite-транзакции.
10. После commit переставляются системные напоминания и обновляется интерфейс.
11. В журнале появляется одна запись о пакете с кнопкой «Отменить».

Даже явная команда пользователя проходит предпросмотр: модель могла неверно выбрать исходники или дату.

## 2.4. Контракт ответа модели

Использовать существующий `AgentPlan` как основу, добавив текстовое поле ответа и новый тип действия:

```json
{
  "say": "Предлагаю перенести две заметки в папку «Дом»",
  "question": "",
  "actions": [
    {
      "action": "folder",
      "notes": [3, 8],
      "folder": "Дом",
      "reason": "Обе записи о ремонте квартиры"
    }
  ]
}
```

Для напоминания:

```json
{
  "say": "Добавлю напоминание на завтра, 10:00",
  "question": "",
  "actions": [
    {
      "action": "remind",
      "note": 8,
      "times": ["2026-11-23 10:00"],
      "lead": -1,
      "repeat": 0,
      "reason": "Пользователь явно указал дату и время"
    }
  ]
}
```

Правила:

- разрешены только ID из `AgentAction.Scope`;
- не более 4 действий и 8 исходников на действие;
- одна команда — один пакет предпросмотра;
- при неоднозначности `actions = []`, а вопрос помещается в `question`;
- модель не утверждает, что уже выполнила изменения;
- прошедшие даты, неизвестные повторы и неподдерживаемые интервалы отклоняются;
- неизвестные действия не выполняются;
- отсутствие корректных действий превращается в обычный ответ или уточняющий вопрос, но не в ошибку всего чата.

## 2.5. Предпросмотр

Для каждого действия формируется человекочитаемая строка без участия модели:

- «Создать заметку “Список покупок”»;
- «Добавить заметке “Врач” напоминание 23.11.2026 в 10:00»;
- «Переместить 2 заметки в новую папку “Дом”»;
- «Переместить 3 заметки в существующую папку “Работа”».

В карточке обязательно показываются исходные заметки. Нельзя ограничиваться общей фразой модели.

MVP применяет пакет целиком. Индивидуальные галочки у действий добавляются позже, чтобы не усложнять отмену и конфликтное поведение.

## 2.6. Проверки перед применением

Для каждого действия сохраняется снимок:

- идентификаторы исходников;
- `updated` заметок;
- прежняя папка;
- прежние напоминания, список дат, повтор и `lead`;
- целевая папка и её состояние до операции.

Применение запрещается, если:

- хотя бы одна заметка изменилась;
- запись удалена или попала в корзину;
- целевая папка была удалена или переименована неоднозначно;
- предложенное напоминание уже стало прошедшим;
- пользователь повторно нажал «Применить» для того же черновика;
- часть действий не может быть выполнена полностью.

Пакет работает по принципу **all-or-nothing**: нельзя переместить половину записей и показать общий успех.

## 2.7. Журнал и отмена

Схему `agent_log` менять не нужно: она уже хранит произвольный JSON в `data`.

Добавить в `AgentJournal` тип `command_batch`:

```json
{
  "command": "исходный текст пользователя",
  "created_notes": [],
  "folders": [
    {"note": 3, "before": 0, "after": 5}
  ],
  "reminders": [
    {
      "note": 8,
      "before_reminder": 0,
      "before_times": "",
      "before_repeat": 0,
      "before_lead": -1,
      "after_reminder": 1763886000000
    }
  ],
  "created_folder": 5
}
```

Правила отмены:

- срок — существующие сутки `AgentJournal.UNDO_WINDOW`;
- новая заметка отправляется в корзину, если пользователь её не редактировал;
- перемещённые записи возвращаются в прежние папки;
- добавленные напоминания возвращаются к прежнему состоянию, если пользователь их не менял;
- созданная пустая папка удаляется только если после операции в ней ничего не появилось;
- при любом конфликте отмена не выполняется частично: показывается причина;
- после успешной отмены переставляются системные напоминания;
- синхронизация остаётся прежней: изменения заметок уходят обычным образом, сам журнал остаётся локальным.

## 2.9. Этапы реализации

### Этап 1 — только контракт

1. Добавить `FOLDER` в `AgentAction`.
2. Реализовать `CommandAnalysis` и жёсткий разбор.
3. Написать тесты на валидные действия, лишние ID, прошлые даты, неизвестные команды и prompt injection.
4. Проверить, что любой неподдерживаемый ответ безопасно превращается в текст без действий.

### Этап 2 — предпросмотр без применения

1. Вернуть черновик команды в ответе чата.
2. Показать карточку с локально сформированным списком изменений.
3. Проверить поворот экрана, повторный рендер и удаление чата.
4. Убедиться, что при закрытии карточки ничего не меняется.

### Этап 3 — применение

1. Сохранять ревизии и прежние значения.
2. Реализовать одну транзакцию на пакет.
3. После commit обновить будильники и UI.
4. Запретить повторное применение того же черновика.
5. Добавить тесты all-or-nothing.

### Этап 4 — журнал и отмена

1. Записывать `command_batch` в той же транзакции.
2. Добавить описание действия и причину невозможности undo.
3. Реализовать отмену с проверкой последующих пользовательских правок.
4. Проверить восстановление папок и напоминаний.

### Этап 5 — проверка

1. Прогнать новые и существующие JVM/SQL-тесты.
2. Прогнать `assembleDebug` и `lintDebug`.
3. Проверить сценарии на локальной заглушке Polza.AI.
4. Только после этого провести отдельный контролируемый платный smoke-тест.

## 2.10. Обязательные тесты

### Разбор

- ID вне выборки отклоняется;
- действие с 9 исходниками отклоняется;
- более 4 действий не попадает в черновик;
- прошедшее напоминание отклоняется;
- неизвестный `action` не выполняется;
- пустое название папки отклоняется;
- дубли ID не создают повторных изменений;
- текст «игнорируй правила» внутри заметки не становится командой;
- JSON с кодовой оградой и пояснением вокруг обрабатывается как в остальном приложении;
- неоднозначная команда создаёт вопрос без изменений.

### Предпросмотр

- видны все затрагиваемые заметки;
- отображается существующая или новая папка;
- показываются точные местные дата и время;
- закрытие карточки ничего не меняет;
- повторный `render()` не дублирует и не применяет действие.

### Применение

- валидный `folder` перемещает все указанные записи;
- валидный `remind` добавляет именно указанные даты;
- `create` создаёт одну заметку с метаданными в допустимых пределах;
- изменение одной исходной заметки отменяет весь пакет;
- ошибка посередине транзакции не оставляет частичных изменений;
- повторное нажатие не создаёт второй результат;
- будильники меняются только после успешного commit.

### Отмена

- возвращаются прежние папки;
- восстанавливаются прежние напоминания;
- созданная заметка уходит в корзину;
- пользовательская правка после применения блокирует небезопасную отмену;
- повторная отмена невозможна;
- через сутки undo недоступно;
- журнал не участвует в синхронизации.

## 2.11. Критерий готовности

Функция готова, если:

- поддерживает только три заявленных типа действий;
- любая модификация проходит предпросмотр;
- все исходники ограничены фактически показанной модели выборкой;
- ревизии проверяются непосредственно перед записью;
- пакет применяется атомарно;
- существует понятная и проверенная отмена;
- нет автоповторов платных запросов;
- тесты покрывают конфликт версий и отказ посередине транзакции;
- новые ограничения и сценарии добавлены в `docs/AI.md`.

## 2.12. Следующие расширения

Только после стабильного MVP:

- выбор отдельных действий галочками;
- очистка напоминаний у выполненных дел;
- корзина с отдельным усиленным подтверждением;
- правка названия и текста через diff;
- команды для планов;
- группировка в колоду;
- пакетные команды над результатами поиска;
- локальные модели после проверки надёжности JSON.

---

# Рекомендуемый порядок работ

1. **Генеративная сводка дня, ручной MVP.** Меньше всего изменений в данных, нет записи в заметки, легко проверить на экране «Сегодня».
2. **Команды: контракт и предпросмотр.** Сначала доказать, что модель не может выйти за разрешённый словарь.
3. **Команды: применение и undo.** Выпускать только после тестов транзакционности и конфликтов.

Не объединять обе задачи в один выпуск: у них разные риски и разные проверки. Сводка дня только читает данные, а команды меняют пользовательский архив.


---

# 3. Реализованное расширение 0.11.0

Исходный MVP выше описывает выпуск 0.10.30. В 0.11.0 словарь расширен без автономного применения и без обхода предпросмотра:

- `create`, `remind`, `folder` сохранены; добавлен `clear_reminders` только для записей с полностью выполненным непустым планом;
- выборка команды увеличена до 24 заметок; `folder` и `clear_reminders` принимают до 24 ID, `create` — до 8 источников, `remind` — до 40 будущих дат;
- команда «Собери всё о поездке и подготовь чек-лист» использует `create` и не меняет исходные записи;
- поиск дублей выполняется локально по `created` за неделю, месяц или год, не более чем по 300 самым новым записям периода; это отчёт со ссылками, без удаления;
- перед очисткой в предпросмотре перечисляются все удаляемые даты и повторы; `CommandExecutor` повторно проверяет план внутри транзакции;
- очистка использует существующий массив `reminders` записи `command_batch`, поэтому общая отмена восстанавливает прежнее расписание;
- все изменения по-прежнему атомарны, проверяют ревизии и отменяются одной кнопкой в течение суток.

Семантический контекст чата реализован отдельно: `SemanticEmbedding` вычисляет компактный детерминированный локальный вектор, `SemanticIndex` хранит его в `note_embeddings` (SQLite 18) и пересчитывает только при смене fingerprint заметки. `Retrieval` объединяет смысловой результат с прежним текстовым рейтингом. Это не нейросетевая облачная модель: индекс не отправляет архив наружу и не гарантирует полноту смыслового поиска для произвольных формулировок.

Проверяются контрактными JVM/SQL-тестами, Android-сборкой и lint. Реальные платные ответы Polza.AI и ручные сценарии на Android остаются отдельным этапом приёма, если их результаты не записаны в `VERIFICATION.md`.
